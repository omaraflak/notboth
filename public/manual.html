Building a Computer from One Gate

This manual will accompany you to build a computer step-by-step starting from a single logical gate: NAND (not-AND). The manual is here to guide you and tell you what to do next and why, not how to do it. That part is for you to figure out. By the end of this journey, you will have a computer that can run your own programming language.

Before you switch anything on

You will start with a basic NAND gate. From that, in about forty moves, you can build a machine that runs software you wrote in a language you designed.

Three habits are worth adopting from the start.

  • Build small. A component should do one nameable thing. If you cannot name it in one word, it is two components.
  • Test before you move on. Write tests for every chip you build before using it. If you don't, expect troubles along the way!
  • Reuse components. Chips are abstractions that make your job easier. Build upon them, only their interfaces matter.

For each component, a NEEDS mention will tell you which other components you need to build it. However, you will almost always find multiple ways to build the same thing, so this is not a rule to follow but an indication.

Mux

Mux(a, b, sel) → out

MUX gate (multiplexer) allows you to select between one of two signals a or b using a selector sel. You can decide to select either a or b based on the selector value, it doesn't matter as long as you stay consistent throughout.

This is essentially an if condition. Almost every decision your machine ever makes is using this chip underneath.

1.07Needs1.01–1.06

Widen everything to sixteen bits

Not16(in[16]) → out[16] · And16, Or16, Xor16, Mux16, DMux16

Your machine will work on sixteen bits at a time (i.e. a word), not individual bits. Sixteen bits is a good size: big enough to address a useful amount of memory (2^16 = 65536), small enough to wire manually. So each of the gates you just built needs a wide sibling that applies it to every bit position independently.

Some notes:

  • Mux16 is a single selector bit choosing between two entire numbers.
  • Bit 0 is the lowest significant bit in the software simulation you're using.
  • Don't actually create sixteen individual inputs for each chip (although you could), use the bits setting of the input/output to widen them (we call that a bus).
Watch outTest the ends and the middle, not just 0000… and 1111…. A bus wired one bit out of alignment passes both of those and nothing else.

This is how your machine answers "is this number zero?", which is the basis of conditional branching.

II

Arithmetic

Six stages that turn logic into mathematics. This Part ends with the single most important chip in the machine, and it is actually less frightening than its reputation.

2.01Needs1.02, 1.04

HalfAdder

HalfAdder(a, b) → sum, carry

A gate that adds two bits. There are only four cases: 0+0, 0+1, 1+0, and 1+1. Remember those are binary addition, but it works exactly like decimal addition:

  • In decimal, when you go above 9 you loop back to 0.
  • In binary, when you go above 1 you loop back to 0.

Therefore, just like in decimal, for two individual digits you will have a resulting sum and a carry.

2.02Needs1.03, 2.01

FullAdder

FullAdder(a, b, c) → sum, carry

Gate that adds three bits. This will be useful when we extend the adder over the entire 16-bits space, as we will need to sum two digits + a carry from the previous column (still remember how to make an addition on paper?).

2.03Needs2.02

Add16

Add16(a[16], b[16]) → out[16]

Sixteen full adders in a row. This will mimic the extact steps you take when adding two numbers on papers. Now your machine can add two 16-bit numbers, which — using two's complement in 2.05 — means it can also subtract, compare, and count.

Watch outTest the carry chain deliberately!
2.04Needs2.03

Inc16

Inc16(in[16]) → out[16]

A gate to increment a number by one.

The reason is Part III. A program counter spends almost its entire life doing exactly this, once per instruction, forever. Naming the operation now means the counter reads as what it is instead of as a special case of addition.

2.05Needs2.03, 2.04, 1.07

Negative numbers

no new chip — a decision

This stage builds nothing, it settles a question.

You need negative numbers, and you do not want to build a second machine for subtracting. The convention that saves you is two's complement: negate a number by inverting every bit and adding one. Under that convention a - b is literally a + (-b), the adder you already have does both jobs, and comparison becomes subtraction followed by a glance at the result.

Here is 5 being negated, and then added back to itself:

stepbitsvalue
start with 500000000000001015
invert every bit1111111111111010−6
add one1111111111111011−5
add the 5 back00000000000000000

The last row carries a 1 off the top end. Since there are only sixteen bits, the seventeenth has nowhere to go and discarding it is exactly what makes the arithmetic wrap round and come out right.

2.06Needs1.xx, 2.03–2.05

ALU

ALU(x[16], y[16], zx, nx, zy, ny, f, no) → out[16], zr, ng

The arithmetic and logic unit: one box that computes any of a couple of dozen useful functions of two numbers, with control bits selecting which: add, subtract, negate, increment, bitwise-and, bitwise-or, pass one input through, produce a constant.

Six single-bit controls, acting in this order to compute the output out:

  • zx — replace x with zero.
  • nx — invert x (applies after zx).
  • zy — replace y with zero.
  • ny — invert y, (applies after zy).
  • f — the operation: 1 ADDs the two pre-processed inputs, 0 ANDs them.
  • no — invert the answer (NOT) on the way out.

Two extra outputs matter as much as the number itself:

  • zr says if the result is zero.
  • ng says if the result is negative (c.f. two's complement).
Watch outThis is the largest chip so far. Test every control combination you intend to use, with at least one negative operand.
III

Memory

Everything so far has been a function: inputs in, outputs out, no history. This Part breaks that. It is the conceptually hardest stretch of the whole build, and the most worthwhile.

3.01Needsa clear head

The leap into time

no new chip — an idea

Every circuit so far is a pure function of its inputs. None of them can answer "what was it a moment ago?", and yet a computer is nothing but a device for remembering things.

The change is one wire: connect a gate's output back to its own input. A real gate takes time to respond, so the value arriving back is the value from before — and a circuit that can see its own past can hold a state. Memory is not a new kind of component. It is ordinary gates plus delay.

Before you continue, wire a NAND's output to its own input, switch on, and watch. Then slow the clock right down and watch again.

3.02Needs1.00, 3.01

Set-reset latch

SRLatch(set, reset) → q

The SRLatch is the first circuit you'll build that remembers:

  • Set set to 1 and the output q will take that value. Set set to 0 and q won't change.
  • Set reset to 1 and the output q will be released and back to 0. Set reset to 0 and q won't change.

You can actually build this from NAND gates or NOR gates. With NOR gates, everything happens as described above. With NAND gates however, the active state for set and reset is 0 not 1 (so you have to set set to 0 to flip q from 0 to 1, and you have to set reset to 0 to flip q from 1 to 0).

While a circuit with NOR seems more intuitive, you should still go with NAND for performance reasons (NOR is not a primitive, it's built out of NANDs).

The SRLatch gate is implemented very simply with two NANDs cross-feeding their outputs into their inputs.

They, however, have two flaws:

  • The right-hand end of the picture is the first flaw: we can assert (i.e. set in the active state) both inputs set and reset, in which case it's not clear what q should be (set is asking for 1, while reset is asking for 0). This is a design flaw.
  • The second flaw is what happens on the way out of that state: release both set and reset at once (i.e. go from 0 to 1 quickly for both inputs) and the two gates are perfectly symmetric with no way to choose, which shows up in the simulation as an oscillation. Real hardware breaks the tie with manufacturing imperfection.
3.03Needs1.00, 1.01, 3.02

Data latch

DLatch(d, enable) → q

DLatch takes a single data input instead of two (set/reset in the SRLatch), plus an enable bit:

  • d — the value to store.
  • enable — while it is high the output q follows d; when it drops, q holds on whatever value it had.
  • q — the stored bit.

The first flaw of the previous model automatically disappears since we can't have contradictory inputs, i.e. asking for a 0 and 1 at the same time.

However, one problem remains: while enable is high the chip is transparent (it let's the d signal pass through). If you chain multiple DLatches and open the gates (enable set to 1), a value can race down the whole chain in one go instead of moving step-by-step — which is undesirable because the machine relies on a value crossing exactly one storage element per tick (whereas here, how far a value travels depends only on gate delays).

3.04Needs3.03, the clock

Flip-flop

DFF(d, clk) → q

The most important idea in the sequential half of this build. A flip-flop samples its input at one instant and holds it steady for the rest of the cycle. Never transparent.

  • d — read only at the edge. What it does between edges is ignored, and that is not a side effect but the entire specification.
  • clk — the clock. This one acts on the rising edge.
  • q — whatever d was at the last edge.

Read the picture at the dashed lines and nowhere else: d moves seven times, q moves three, always at an edge and always to whatever d was at that instant.

Use the rising edge. Either works in principle so long as every clocked part of the machine agrees on one, and the built-in RAM writes on the rise — so that is the agreement already on the table. Mixing the two gives a bug that presents as a timing problem and is very hard to find.

Build it from two gated latches back to back: the first enabled while the clock is low, the second while it is high. Whichever is listening, the other is holding, so a value can only advance one stage per tick. That restriction is what makes the rest of the build tractable — the whole machine changes state together, and every part can rely on the others staying still while it thinks.

When it works, chain a handful, feed the clock, and watch a single 1 march through them one stage per tick.

Watch outGive the clock a period comfortably longer than the deepest path of gates it drives, so the logic has time to settle before the next edge. Too fast a clock does not run your machine faster; it runs it wrongly.
3.05Needs3.04, 1.05

Bit

Bit(in, load, clk) → out

A flip-flop takes whatever arrives, every single tick. What you want is storage that keeps its value until told otherwise.

  • in — the value to store.
  • load — 1 takes in at the next edge, 0 keeps what is already there.
  • clk and out — as in 3.04.

So on each edge, store either the new input or the value already held. Choosing between two values with a control bit is a multiplexer, and the second value comes from the flip-flop’s own output: a one-bit register is a flip-flop with a mux in its feedback path. That is where stage 1.05 pays for itself.

The middle edge is the one to look at. in has gone low and the clock has ticked, either of which would have moved a bare flip-flop, and out does not move — because load was low and the mux was feeding the flip-flop its own output. Storage is the flip-flop plus somewhere for the old value to go round again.

3.06Needs3.05

Register

Register(in[16], load, clk) → out[16]

Sixteen Bits side by side, sharing one load and one clock. Every pin is the one from 3.05 made sixteen bits wide, and it behaves identically: load high takes in at the next edge, low keeps what is there.

Mechanical and quick, and the first component that would be recognisable to someone who has only seen a computer from the software side. It is a variable.

3.07Needs3.06, 1.09, 1.10

RAM8

RAM8(in[16], load, address[3], clk) → out[16]

Eight registers and an address that picks one of them.

  • address[3] — which of the eight.
  • in[16], load, clk — write in into that register on the next edge, if load is high.
  • out[16] — that register’s contents, always. Reading needs no clock; only writing waits for the edge.

Two jobs, and both parts are already on your shelf: route the write signal to exactly one register (a demux) and select one register’s output to present (a wide mux).

Build it and the recursion is visible: RAM64 is eight RAM8s addressed by three more bits, RAM512 is eight RAM64s. Only the depth of the address changes.

Then stop. Having proved you can, use the built-in RAM part for the real machine. It is worth saying why that is a reasonable place to stop: a sixteen-thousand-word memory made of flip-flops is around two and a half million gates, and real hardware does not build it that way either — an SRAM cell is six transistors, not a netlist of gates. You have demonstrated that memory can be made of NANDs. Now buy it off the shelf and spend your gates on the CPU, where the interesting decisions are.

3.08Needs3.06, 2.04, 1.05

Program counter

PC(in[16], load, inc, reset, clk) → out[16]

The register that says which instruction to run next, and the last piece of Part III. Four things can happen to it on a clock edge, and naming all four is most of the specification:

  • reset — out becomes 0. What happens when you switch the machine on.
  • load — out becomes in. A jump, and therefore where every if, every while and every function call eventually comes from.
  • inc — out becomes out + 1. The next instruction, which is what happens on almost every tick a machine ever runs.
  • none of them asserted — out does not change. This one is easy to leave out, because it is the case where nothing is supposed to happen, and leaving it out is the usual way to end up with a counter that will not sit still.

When more than one is asserted, take them in the order above: reset beats load, and load beats inc. Any consistent order can be made to work, but that one agrees with what the words mean — a machine being switched on should not also be jumping, and an instruction that says “jump” should not also step past the place it jumped to. Whichever you choose, write it down, because Part IV will depend on it.

One thing about the shape before you draw it: the incrementer reads out, not in. A counter counts itself. Feed the adder from in and you have built a chip that computes one more than whatever is being loaded, which accumulates nothing and sits at the same number for ever. It is the same arrangement as 3.05 one size up: the register’s own output goes back round into the thing that decides its next input, and that loop is the whole of what makes it a counter rather than a register.

With that settled it is a register with a stack of muxes in front of it, one per behaviour, and stage 1.05 paying for itself yet again.

Watch outAll three controls have to make the register store, not just choose a value. Wire the register’s load to the chip’s load alone and inc and reset will compute exactly the right number and then throw it away, which looks like a broken incrementer and is not one. One way out: store on every edge, and let the muxes hand the register its own output when nothing is asserted — then “do not change” needs no gates of its own.
IV

The machine

You now own every component a computer is made of. What remains is deciding what your computer is — and that is a design problem, not a wiring problem.

4.01Needspaper

Design the instruction set first

no new chip — a specification

Do not wire anything in this Part until you have written down your instruction set. The hardware is a consequence of the instruction set, not the other way round, and every hour spent here saves several later.

What you are deciding: how wide an instruction is, what an instruction can say, and how few kinds of instruction you can get away with. Fewer is dramatically better — every additional instruction format is more decoding logic and more ways to be wrong.

One proven shape, worth understanding before you invent your own: two instruction types, distinguished by a single bit. One loads a constant into a register. The other says “compute something, put the answer somewhere, and maybe jump” — with separate little fields for what to compute, where to put it, and when to jump. Two formats is enough for a real computer, and every format you add is more decoding logic in 4.04.

4.02Needs4.01

The memory map

no new chip — a decision

Decide what lives at which addresses, and write that down too. Some region is working memory. If you want a screen or a keyboard, they get addresses as well.

That last point is worth dwelling on. If a screen is simply a range of memory addresses whose contents happen to be displayed, then drawing a pixel is storing a number, and you need no new instructions, no new hardware path, and no concept of input or output at all. It is one of the tidiest economies in the design, and it costs nothing but a decision made now.

4.03Needs3.06, 4.01

Two registers

no new chip — two Registers from 3.06

Your CPU needs somewhere to hold values it is working on. Two registers is enough, and each has a distinct character worth respecting.

One holds data — a number being worked on. The other does double duty: it holds either a value, or an address — which memory location to read or write, or which instruction to jump to. That double duty is what lets a machine with almost no instructions still reach any part of memory. To use a memory location, you first put its address in that register, then operate.

Sixteen bits of storage each, a load signal each. You already built these.

4.04Needs4.01

The decoder is mostly wires

Decode(instruction[16]) → zx, nx, zy, ny, f, no, useM, loadA, loadD, writeM, jump[n]

“Instruction decoding” sounds like it needs a large and clever chip. With a well-chosen instruction set it needs almost nothing: the bits of the instruction are the control signals. The field that says what to compute is wired straight to the ALU’s control inputs. The field that says where to store the answer is wired straight to the load inputs of the registers.

The only real logic is a handful of gates deciding which instruction type you are looking at, and gating the control signals accordingly — because a constant-loading instruction must not accidentally trigger a memory write.

That list of outputs is not a choice. It is fixed by what your machine already has that needs controlling: the ALU’s six bits from 2.06, a load line for each of the two registers, whether memory is written, whether the ALU’s second input comes from memory or from the address register (useM), and the jump field passed on to 4.06. What is yours is which instruction bits produce them, and how wide the jump field is — the n in the signature is whatever your table in 4.01 says.

If this chip is turning out large, the problem is upstream in 4.01. Go back and simplify the encoding; that is much cheaper than building the decoder it demands.

4.05Needs2.06, 4.03, 4.04

The datapath

CPU(instruction[16], inM[16], clk) → outM[16], writeM, addressM[15], pc[15]

Now assemble the CPU. This is the largest chip you will draw. It can look like too much at first; it helps that everything in it is a part you have already built and tested.

The structure is a loop. The ALU takes two inputs — one always from the data register, the other selected between the address register and a value fetched from memory. Its output goes back to the registers and out to memory. Which of those actually happen is decided by the control bits from 4.04. Every one of those choices is a mux; every mux is stage 1.05.

Work in the order the signal flows and test as you go: get the ALU fed correctly first, then get its output stored correctly, then worry about jumps.

Watch outThe single most common bug here is a value being read in the same tick it is written. Sketch on paper what is stable when. This is exactly the discipline the flip-flop bought you in 3.04 — use it.
4.06Needs4.05, 3.08

Jumps

Jump(zr, ng, jump[n]) → load

The last piece of the CPU, and the one that turns a calculator into a computer. Your ALU reports two facts about its result: it was zero (zr) and it was negative (ng). Your instruction carries a small field saying which outcomes should cause a jump. Compare the two, and if they agree, tell the program counter to load instead of increment.

That handful of gates is where every if, every while, every function call and every loop in every program that will ever run on this machine comes from.

4.07Needs4.02

Talking to the world

no new chip — a region of RAM that something else is watching

Optional, and worth it. If you reserved addresses for a screen and a keyboard back in 4.02, wire them up now — a region of memory whose contents are displayed, and a location that holds whichever key is currently down.

Notice that the CPU needs no changes whatsoever. It has no idea a screen exists. It stores a number at an address, exactly as it always does, and something else is watching.

4.08Needs4.05, 4.06, 3.07

The computer

Computer(reset, clk) → nothing — the output is what it leaves in memory

Three boxes and the wires between them: a ROM holding the program, the CPU, and the RAM. The counter’s output addresses the ROM; the ROM’s output is the instruction; the CPU’s memory outputs go to the RAM and back.

Keeping instructions and data in separate memories is a real architectural choice, called Harvard, and what it buys you is simplicity: the machine can fetch an instruction and touch data in the same tick without them queuing for the same memory. The cost is that a program cannot modify itself, which is rarely a loss at this scale.

Wire it up. Then stop, because you have built a computer, and there is nothing left to add to the hardware. Everything after this is software.

V

Software

The hardware is finished and will not change again. Everything from here is built on top of it, in layers, each one making the next one bearable.

5.01Needs4.08

A program in binary

your instruction table → bits in the ROM, by hand

Write something tiny directly in machine code — add two numbers and store the result — encode it by hand from your table in 4.01, load it into the ROM, and run it.

Do this exactly once. It is the moment the hardware stops being a diagram and becomes a machine, and it will teach you more about your instruction set in ten minutes than an afternoon of staring at it. It is also the quickest way to see why you want an assembler, which is the point.

5.02Needs5.01

The assembler

text → machine code

A program that turns readable mnemonics into the bits you just encoded by hand. Write it in whatever language you like; it runs on your own computer, not on the one you built.

Two features earn their keep immediately: symbolic names for instructions, and labels for addresses, so that a jump target is @loop and not the number 47 — a number that changes the moment you insert a line. Everything else is optional.

This is also the first opportunity to write a real test: assemble the program from 5.01 and check you get the same bits you produced by hand.

5.03Needs5.02

A stack, and a convention for calling things

a region of RAM, plus rules → functions that can call functions

Functions need somewhere to keep their local variables and their return address, and it must nest — a function can call a function that calls a function. A stack is the structure that does this, and it is not hardware: it is a region of RAM plus a register holding a pointer to the top of it, plus a set of rules everyone agrees to follow.

Design the rules deliberately and write them down: who pushes the arguments, who saves what, where the return value lives, who cleans up. This is the bridge between a machine that runs instructions and a machine that runs programs, and almost every hard bug in the rest of the project will be a violation of these rules.

5.04Needs5.03

An intermediate language

stack operations → assembly

A small stack-based language — push, pop, add, compare, call, return — and a translator from it into your assembly.

Skipping this layer is a common way for the project to stall. Compiling a high-level language directly to machine code means every language feature has to be solved in the same breath as every hardware detail, and the two problems tangle. This layer cuts the knot: the compiler above it only has to think about meaning, and this translator only has to think about your CPU. Each half becomes something you can hold in your head.

5.05Needs5.04

The compiler

your language → the intermediate language

Now design a language you would actually enjoy writing, and compile it down one level. Variables, expressions, if, while, functions, and some way to group data together. That is enough for real programs; resist adding more until you have run something.

Because you are targeting the intermediate language rather than the metal, each construct becomes a small, local translation — a while is a couple of labels and a conditional jump, an expression is a walk over its own tree emitting pushes. That keeps each construct small enough to hold in your head.

5.06Needs5.05

A runtime

your language → multiply, divide, allocate, draw

Your hardware can add. It cannot multiply, divide, allocate memory or draw a line. Those are library functions, written in your own language, and this is the layer people forget to budget for.

Multiplication is repeated addition until you make it cleverer. Division is the same in reverse. Memory allocation is bookkeeping over a region of RAM. Each one is a small program, and writing them is the first time you get to use the thing you built rather than build it.

5.07Needs5.06

Primes

your language → the primes below a thousand

Write a sieve, in your language, and print the primes below a thousand.

When it runs, trace what actually happened. A number you typed was compiled to a stack language, translated to assembly, assembled into bits, stored in a ROM you configured, fetched by a counter you designed, decoded by wires you placed, and computed by an arithmetic unit that is, at the bottom, some thousands of copies of a single gate that only knows how to say “not both”.

There is no part of that chain you took on trust.
