Building a Computer from One Gate

This manual will accompany you to build a computer step-by-step starting from a single logical gate: NAND (not-AND). The manual is here to guide you and tell you what to do next and why, not how to do it. That part is for you to figure out. By the end of this journey, you will have a computer that can run your own programming language.

This tutorial is largely insipired by Nand2Tetris' designs.

Before you switch anything on

You will start with a basic NAND gate. From that, in about forty moves, you can build a machine that runs software you wrote in a language you designed.

Three habits are worth adopting from the start.

  • Build small. A component should do one nameable thing. If you cannot name it in one word, it is two components.
  • Test before you move on. Write tests for every chip you build before using it. If you don't, expect troubles along the way!
  • Reuse components. Chips are abstractions that make your job easier. Build upon them, only their interfaces matter.

For each component, a NEEDS mention will tell you which other components you need to build it. However, you will almost always find multiple ways to build the same thing, so this is not a rule to follow but an indication.

1.07Needs1.01–1.06

Widen everything to sixteen bits

Not16(in[16]) → out[16] · And16, Or16, Xor16, Mux16, DMux16

Your machine will work on sixteen bits at a time (i.e. a word), not individual bits. Sixteen bits is a good size: big enough to address a useful amount of memory (2^16 = 65536), small enough to wire manually. So each of the gates you just built needs a wide sibling that applies it to every bit position independently.

Mux16 is a single selector bit choosing between two entire numbers.

Bit 0 is the lowest significant bit in the software simulation you're using.

Don't actually create sixteen individual inputs for each chip (although you could), use the bits setting of the input/output to widen them (we call that a bus).

Watch outTest the ends and the middle, not just 0000… and 1111…. A bus wired one bit out of alignment passes both of those and nothing else.

II

Arithmetic

Six stages that turn logic into mathematics. This Part ends with the single most important chip in the machine, and it is actually less frightening than its reputation.

2.01Needs1.02, 1.04

HalfAdder

HalfAdder(a, b) → sum, carry

Gate that adds two bits. There are only four cases: 0+0, 0+1, 1+0, and 1+1. Remember those are binary addition, but it works exactly like decimal additions:

  • In decimal, when you go above 9 you loop back to 0.
  • In binary, when you go above 1 you loop back to 0.

Therefore, just like in decimal, for two individual digits you will have a resulting sum and a carry.

2.02Needs1.03, 2.01

FullAdder

FullAdder(a, b, c) → sum, carry

A gate that adds three bits. This will be useful when we extend the adder over the entire 16-bits space, as we will need to sum two digits + a carry from the previous column (remember how to make an addition on paper?).

2.03Needs2.02

2.05Needs2.03, 2.04, 1.07

Negative numbers

no new chip — a decision

This stage builds nothing, it settles a question.

You need negative numbers, and you do not want to build a second machine for subtracting. The convention that saves you is two's complement: negate a number by inverting every bit and adding one. Under that convention a - b is a + (not b), and the adder you already is enough.

Here is 5 being negated, and then added back to itself:

stepbitsvalue
start with 500000000000001015
invert every bit1111111111111010−6
add one1111111111111011−5
add the 5 back00000000000000000

The last row carries a 1 off the top end. Since there are only sixteen bits, the seventeenth has nowhere to go and discarding it is exactly what makes the arithmetic wrap round and come out right (i.e. 5 + (-5) = 0).

2.06Needs1.xx, 2.03–2.05

ALU

ALU(x[16], y[16], zx, nx, zy, ny, f, no) → out[16], zr, ng

The arithmetic and logic unit: one box that computes any of a couple of dozen useful functions of two numbers, with control bits selecting which: add, subtract, invert, increment, bitwise-and, bitwise-or, pass one input through, produce a constant.

Six single-bit controls, acting in this order to compute the output out:

  • zx — replace x with zero.
  • nx — invert x (applies after zx).
  • zy — replace y with zero.
  • ny — invert y, (applies after zy).
  • f — the operation: 0 ANDs the two pre-processed inputs, 1 ADDs them.
  • no — invert the answer (NOT) on the way out.

Two extra outputs matter as much as the number itself:

  • zr says if the result is zero.
  • ng says if the result is negative (c.f. two's complement).

Since there are 6 control bits, that's 2^6=64 different operations supported! These are some useful ones:

III

Memory

Everything so far has been a function: inputs in, outputs out, no history. This Part breaks that. It is the conceptually hardest stretch of the whole build, and the most worthwhile.

3.01Needsa clear head

The leap into time

no new chip — an idea

Every circuit so far is a pure function of its inputs. None of them have states or can remember.

To get there, the trick is to connect a gate's output back to its own input. A real gate takes time to respond, so the value arriving back is the value from before. A circuit that can see its own past can hold a state.

Before you continue, wire a NAND's output to its own input, switch on, and watch.

3.02Needs1.00, 3.01

Set-reset latch

SRLatch(set, reset) → q

The SRLatch is the first circuit you'll build that remembers:

  • Set set to 1 and the output q will lock in that value. Flipping set again to 0/1 won't affect q.
  • Set reset to 1 and the output q will be released and back to 0. Flipping reset to 0/1 after that won't affect q.

You can actually build this from NAND gates or NOR gates. With NOR gates, everything happens as described above. With NAND gates however, the active / trigger state for set and reset is 0 instead of 1 (so you have to set set to 0 to flip q from 0 to 1, and you have to set reset to 0 to flip q from 1 to 0).

While a circuit with NOR seems more intuitive, you should still go with NAND for performance reasons (NOR is not a primitive, it's built out of NANDs).

The SRLatch gate is implemented very simply with two NANDs cross-feeding their outputs into their inputs.

They, however, have two flaws:

  • The right-hand end of the picture is the first flaw: we can lower (i.e. set to 0, the active state) both set and reset, in which case it's not clear what q should be (set is asking for 1, while reset is asking for 0). This is a design flaw.
  • The second flaw is what happens on the way out of that state: release both set and reset at once (i.e. go from 0 to 1 quickly for both inputs) and the two gates are perfectly symmetric with no way to choose. This shows up in the simulation as an oscillation, while real hardware breaks the tie with manufacturing imperfection.
3.03Needs1.00, 1.01, 3.02

Data latch

DLatch(d, enable) → q

DLatch takes a single data input d instead of two (set/reset in the SRLatch), plus an enable bit:

  • d — the value to store.
  • enable — while it is high the output q follows d; when it drops, q holds on whatever value it had.
  • q — the stored bit.

The first flaw of the previous model automatically disappears since we can't have contradictory inputs, i.e. asking for a 0 and 1 at the same time.

However, one problem remains: while enable is high the chip is transparent (it let's the d signal pass through). If you chain multiple DLatches and open the gates (enable set to 1), a value can race down the whole chain in one go instead of moving step-by-step. This is undesirable because the machine relies on a value crossing exactly one storage element per tick (whereas here, how far a value travels depends only on gate delays).

3.04Needs1.01, 3.03

Flip-flop

DFF(d, clk) → q

A flip-flop samples its input at one instant using a clock and outputs it for the rest of the clock cycle.

We're using the notion of a clock here for the first time. This is a normal input (not the actual clock chip given to you in the interface), but you should expect the signal itself to be passed down from an actual clock chip higher up in the chain. So the clk input is a signal that goes up then down periodically.

  • d — data signal to be held on to. Read it only at the rising edge of the clock. What it does during the cycle should be ignored.
  • clk — the clock signal. When the clock goes from low to high (i.e. rising edge) is when you sample the d value and write it to q.
  • q — whatever d was at the last edge.

Read the picture at the dashed lines: d moves seven times, q moves three, always at a rising edge of clk and always to whatever d was at that instant.

So the real difference with the DLatch gate is that we write d to q only at the rising edge of the clock, and not before or after. So while the clock is up, unlike the DLatch, we won't write changes in d to q. This fixes the transparency issue of the DLatch and we now have the building block of a Bit!

Hint: you only need two DLatch gates to build a Flip-Flop.

Watch outGive the clock a period comfortably longer than the deepest path of gates it drives, so the logic has time to settle before the next edge. This holds for tests as well.
3.05Needs1.05, 3.04

Bit

Bit(in, load, clk) → out

A flip-flop copies the data, whatever it is, every single tick. So if d doesn't happen to hold what you want to write during a rising edge of the clock, you are in a bad position because it is written to q anyways!

What you want is storage that keeps or discards its value only if you ask it to. This is the Bit!

  • in — the value to store.
  • load — 1 will write in to out at the next rising edge of clk, while 0 should hold the value of out.
  • clk — same as in 3.04.
  • out — same as in 3.04.

So on each rising edge, store either the new input or the value already held.

The middle edge is the one to look at. in has gone low and the clock has ticked, but because load is also low, out remains unchanged.

3.06Needs3.05

Register

Register(in[16], load, clk) → out[16]

A Register holds on to a word: sixteen Bits side by side, sharing one load and one clk.

You now have a way to store variables!

Watch outRemember to uses buses, and not sixteen individual inputs/outputs!
3.07Needs1.09, 1.10, 3.06

RAM8

RAM8(in[16], load, address[3], clk) → out[16]

Eight registers and an address that picks one of them.

  • in[16] — data to write on the next rising edge of the clock if load is high.
  • load — same as in 3.06.
  • address[3] — which of the eight registers to write to.
  • clk — same as in 3.06.
  • out[16] — that register's content.

Build it and the recursion is visible: RAM64 is eight RAM8s addressed by three more bits, RAM512 is eight RAM64s. Only the depth of the address changes.

Then stop! Having proved you can build RAM out of NANDs, use the built-in RAM part for the real machine. A register is about ~300 gates, so building a 16kB memory would be over ~2.4M gates!

3.08Needs1.03, 1.05 (1.07), 2.04, 3.06

Program counter

PC(in[16], load, inc, reset, clk) → out[16]

The program counter is a special register that says which instruction to run next in your CPU (by holding on to the instruction address). Four things can happen to it on the rising edge of the clock:

  • reset — out becomes 0. What happens when you switch the machine on.
  • load — out becomes in. This is how you would jump from one instruction address to another.
  • inc — out becomes out + 1. Point to the next instruction, which is what happens on almost every tick a machine ever runs.
  • None of reset/load/inc are set — out should hold on its value.

When more than one control bit is set, take them in the order above: reset beats load, and load beats inc. Any consistent order can be made to work, but that one is easy to make sense of:

  • A machine being switched on should not also be jumping to a non-zero address.
  • An instruction that says "jump" should not also step past (i.e. inc) the place it just jumped to.
Watch outAll three controls have to make the register store, not just choose a value.
IV

The machine

In this Part, we design the CPU instruction set, and build the CPU and the machine around it. If you are unfamiliar with the concepts of instructions and state-machines, I would advise to have a look at my article on Virtual Machines.

4.01Needs3.06, 3.07, 3.08

Machine registers

no new chip — the three registers

Our machine will need only three registers to function properly:

  • A — an address register (3.06). This register can hold an address pointing to the RAM or a data value directly. The interpretation of A's content will depend on the instruction using it.
  • D — a data register (3.06). This register holds only data.
  • PC — a program counter (3.08). This register holds the address of the instruction to execute next.
4.02Needs2.06, 4.01

Instruction set

no new chip — the encoding of instructions

We'll present an instruction set and design ready to implement, but once you understand this it'll be much easier to implement your own.

In this design, an instruction is 16 bits and we'll support two instruction layouts. Those two formats are differentiated by the 15th (most significant) bit of the instruction.

instruction[15] = 0

When that most significant bit is 0, then we simply write the 15 remaining bits to register A (zero-extended to 16 bits), and nothing else.

Since we're left with 15 bits, A can therefore contain values between 0 and 32767.

instruction[15] = 1

When that most significant bit is 1, the instruction will:

  1. Compute something with the ALU.
  2. (optionally) Store the result into one or multiple registers.
  3. (optionally) Jump the program counter register PC to some address.

Here's the format of the instruction:

  • Unused bits. Bits 13 and 14 have no use in the format, and could be put to 0 or 1.
  • Address. We said earlier that register A could contain an address (pointing to data in the RAM) or plain data. Bit 12 is set to 1 when the value of A is an address, and set to 0 when the value of A is plain data.
  • Control. Bits 6-11 are the 6 control bits the ALU uses and they define the performed computation. In order: zx, nx, zy, ny, f, no. The computation is performed on the following inputs: the ALU's x input is always the content of register D; the ALU's y input is either the content of register A when a=0 or the content of the RAM data pointed by A when a=1.
  • Destination. Bits 3-4-5 are independent bits each telling whether to write the ALU's output to A, D, and/or the RAM's register pointed by A.
  • Jump. Lastly, these are 3 bits each telling whether to load the address in A into the program counter register PC. Remember that the ALU outputs a number but also zr (output is zero) and ng (output is negative). If instruction bit 2 is set, then we should load PC if ng is set. If instruction bit 1 is set, then we should load PC if zr is set. Finally, if instruction bit 0 is set, then we should load PC if neither zr nor ng are set.

One instruction decoded

4.04Needs4.02

Jumps

Jump(zr, ng, j1, j2, j3) → load

This gate is just to declutter the CPU implementation. It decides whether the program counter PC should load instead of increment.

This decision is based on the ALU's two status outputs and the three gated jump bits from 4.02:

  • If j3 is set, then we should load PC if ng is set.
  • If j2 is set, then we should load PC if zr is set.
  • If j1 is set, then we should load PC if neither zr nor ng are set.
4.05Needs2.06, 4.xx

CPU

CPU(instruction[16], inM[16], reset, clk) → outM[16], writeM, addressM[16], pc[16]

At last, the CPU! Its circuit holds registers A and D, the ALU, Decode, Jump, and the program counter PC.

Its job is to take an instruction, decode it, execute it, read/write to registers A/D and/or RAM, and increment or jump the program counter PC.

The inputs are:

  • instruction — the 16-bit instruction to execute.
  • inM — the value of a register in the RAM (fetched at addressM, outputted at the previous turn).
  • reset — to reset the program counter PC.
  • clk — the clock running the whole machine.

The outputs are:

  • outM, writeM, addressM — The value outM is be written to the RAM at addressM if writeM=1.
  • pc — the value of the PC register after being incremented or loaded, i.e. the address of the next instruction.
Watch outRemember to explicitly handle the case where op=0, i.e. load register A with the 15 bit value of the instruction.
4.06Needs3.07, 4.06

The computer

Computer(reset, clk) → nothing

The final computer, three chips: CPU, RAM, ROM.

Use the built-in RAM and ROM.

  • The program to execute lives in the ROM.
  • The reset bit will set the PC counter inside the CPU to zero. It boots the machine.
  • The CPU outputs that initial pc which it feeds into the ROM to get the value of the instruction.
  • The instruction fetched from the ROM simply goes back into the CPU to be executed.
  • The RAM is wired to the CPU's writeM/addressM/outM fields.
V

Software

The hardware is finished and will not change again. Everything from here is built on top of it, in layers, each one making the next one bearable.

5.01Needs4.08

A program in binary

the instruction set from 4.02 → bits in the ROM, by hand

Write something tiny directly in machine code — add two numbers and store the result — encode it by hand from the tables in 4.02, load it into the ROM, and run it.

Do this exactly once. It is the moment the hardware stops being a diagram and becomes a machine, and it will teach you more about your instruction set in ten minutes than an afternoon of staring at it. It is also the quickest way to see why you want an assembler, which is the point.

5.02Needs5.01

The assembler

text → machine code

A program that turns readable mnemonics into the bits you just encoded by hand. Write it in whatever language you like; it runs on your own computer, not on the one you built.

Two features earn their keep immediately: symbolic names for instructions, and labels for addresses, so that a jump target is @loop and not the number 47 — a number that changes the moment you insert a line. Everything else is optional.

This is also the first opportunity to write a real test: assemble the program from 5.01 and check you get the same bits you produced by hand.

5.03Needs5.02

A stack, and a convention for calling things

a region of RAM, plus rules → functions that can call functions

Functions need somewhere to keep their local variables and their return address, and it must nest — a function can call a function that calls a function. A stack is the structure that does this, and it is not hardware: it is a region of RAM plus a register holding a pointer to the top of it, plus a set of rules everyone agrees to follow.

Design the rules deliberately and write them down: who pushes the arguments, who saves what, where the return value lives, who cleans up. This is the bridge between a machine that runs instructions and a machine that runs programs, and almost every hard bug in the rest of the project will be a violation of these rules.

5.04Needs5.03

An intermediate language

stack operations → assembly

A small stack-based language — push, pop, add, compare, call, return — and a translator from it into your assembly.

Skipping this layer is a common way for the project to stall. Compiling a high-level language directly to machine code means every language feature has to be solved in the same breath as every hardware detail, and the two problems tangle. This layer cuts the knot: the compiler above it only has to think about meaning, and this translator only has to think about your CPU. Each half becomes something you can hold in your head.

5.05Needs5.04

The compiler

your language → the intermediate language

Now design a language you would actually enjoy writing, and compile it down one level. Variables, expressions, if, while, functions, and some way to group data together. That is enough for real programs; resist adding more until you have run something.

Because you are targeting the intermediate language rather than the metal, each construct becomes a small, local translation — a while is a couple of labels and a conditional jump, an expression is a walk over its own tree emitting pushes. That keeps each construct small enough to hold in your head.

5.06Needs5.05

A runtime

your language → multiply, divide, allocate, draw

Your hardware can add. It cannot multiply, divide, allocate memory or draw a line. Those are library functions, written in your own language, and this is the layer people forget to budget for.

Multiplication is repeated addition until you make it cleverer. Division is the same in reverse. Memory allocation is bookkeeping over a region of RAM. Each one is a small program, and writing them is the first time you get to use the thing you built rather than build it.

5.07Needs5.06

Primes

your language → the primes below a thousand

Write a sieve, in your language, and print the primes below a thousand.

When it runs, trace what actually happened. A number you typed was compiled to a stack language, translated to assembly, assembled into bits, stored in a ROM you configured, fetched by a counter you designed, decoded by wires you placed, and computed by an arithmetic unit that is, at the bottom, some thousands of copies of a single gate that only knows how to say “not both”.

There is no part of that chain you took on trust.
