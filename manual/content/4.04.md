---
num: 4.04
title: The decoder is mostly wires
sig: Decode(instruction[16]) → zx, nx, zy, ny, f, no, useM, loadA, loadD, writeM, jump[n]
needs: 4.01
short: The decoder is wires
---

“Instruction decoding” sounds like it needs a large and clever chip. With a
well-chosen instruction set it needs almost nothing: the bits of the
instruction *are* the control signals. The field that says what to compute is
wired straight to the ALU’s control inputs. The field that says where to store
the answer is wired straight to the load inputs of the registers.

The only real logic is a handful of gates deciding which instruction type you
are looking at, and gating the control signals accordingly — because a
constant-loading instruction must not accidentally trigger a memory write.

That list of outputs is not a choice. It is fixed by what your machine already
has that needs controlling: the ALU’s six bits from 2.06, a load line for each
of the two registers, whether memory is written, whether the ALU’s second
input comes from memory or from the address register (`useM`), and the jump
field passed on to 4.06. What *is* yours is which instruction bits produce
them, and how wide the jump field is — the `n` in the signature is whatever
your table in 4.01 says.

If this chip is turning out large, the problem is upstream in 4.01. Go back
and simplify the encoding; that is much cheaper than building the decoder it
demands.
