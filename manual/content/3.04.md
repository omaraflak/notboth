---
num: 3.04
title: Flip-flop
sig: DFF(d, clk) → q
needs: 3.03, the clock
---

The most important idea in the sequential half of this build. A flip-flop
samples its input at one *instant* and holds it steady for the rest of the
cycle. Never transparent.

- **d** — read only at the edge. What it does between edges is ignored, and
  that is not a side effect but the entire specification.
- **clk** — the clock. This one acts on the **rising** edge.
- **q** — whatever `d` was at the last edge.

```wave
!Timing diagram for the flip-flop
clk      1100110011001100
d        1001110001110100
>q       0000111100001111
@4 read
@8 read
@12 read
```

Read the picture at the dashed lines and nowhere else: `d` moves seven times,
`q` moves three, always at an edge and always to whatever `d` was at that
instant.

Use the rising edge. Either works in principle so long as every clocked part
of the machine agrees on one, and the built-in RAM writes on the rise — so
that is the agreement already on the table. Mixing the two gives a bug that
presents as a timing problem and is very hard to find.

Build it from two gated latches back to back: the first enabled while the
clock is *low*, the second while it is high. Whichever is listening, the other
is holding, so a value can only advance one stage per tick. That restriction
is what makes the rest of the build tractable — the whole machine changes
state together, and every part can rely on the others staying still while it
thinks.

When it works, chain a handful, feed the clock, and watch a single 1 march
through them one stage per tick.

::: watch
Give the clock a period comfortably longer than the deepest path of gates it
drives, so the logic has time to settle before the next edge. Too fast a clock
does not run your machine faster; it runs it wrongly.
:::
